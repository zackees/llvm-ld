# llvm-ld — agent guide

A C-ABI DLL wrapping the pinned LLVM LLD COFF/MinGW drivers. First-party code is ~50 files under
`src/`, `include/`, `cmake/`, `tools/`, `tests/`, `.github/`. Everything else (5,600+ files under
`llvm-project/`) is a SHA-locked vendored payload. Read `PROVENANCE.md` before touching the payload.

## The vendored payload is read-only (decided; do not relitigate)

`llvm-project/**` is upstream LLVM `llvmorg-23.1.0`, pruned, byte-identical to upstream except for
the five CMake patches listed in `provenance/payload-prune.json` (`patched`). `tools/verify.py`
hashes every payload file against `provenance/llvm-source-closure.json` and CI fails on any drift.

- Never edit, reformat, or "refactor" anything under `llvm-project/` or `upstream/`.
- Never hand-edit `provenance/*.json`; they are generated by `tools/import.py` /
  `tools/audit_build.py`.
- If an upstream change is genuinely needed (e.g. a cherry-picked perf fix), the path is: apply
  the edit with `Read --offset/--limit` + `Edit`, regenerate `llvm-source-closure.json`, and add a
  `patched` entry to `payload-prune.json` in the same commit. Never read a multi-MB file whole.

## Optimization targets — where the hot path actually is

This was investigated (Sep 2026). For a normal object-file link, the code that executes is:

- `llvm-project/lld/COFF/*` — `Writer.cpp`, `PDB.cpp`, `DebugTypes.cpp`, `InputFiles.cpp`,
  `SymbolTable.cpp`, `Chunks.cpp`, `ICF.cpp`, `MarkLive.cpp` (largest is 118 KB)
- `llvm-project/llvm/lib/DebugInfo/{PDB/Native,CodeView,MSF}` — PDB emission, usually the #1 hotspot
- `llvm-project/llvm/lib/Object/{COFFObjectFile,Archive,WindowsResource}.cpp`
- `llvm-project/llvm/lib/Support/{Parallel,MemoryBuffer,xxhash,StringMap,Allocator}.cpp`,
  `Support/Windows/*.inc`
- `llvm-project/lld/COFF/LTO.cpp` and `llvm-project/llvm/lib/LTO/*` for LTO tuning knobs

The multi-MB files (`Target/X86/X86ISelLowering.cpp`, `CodeGen/SelectionDAG/*`,
`Transforms/**`, `Analysis/*`, `IR/*`, `Support/UnicodeNameToCodepointGenerated.cpp`, all `.td`)
are compiled into the DLL but are **inert during a non-LTO link**. During LTO they are LLVM's
optimizer/backend, not the linker; a hotspot there is an upstream issue, not a local edit, and
issue #6 gates LTO output on byte-identity with a pinned clang-cl so codegen changes would break
the correctness gate. Binary-size/build-time wins in those directories come from CMake
(`LLVM_TARGETS_TO_BUILD`, `/OPT:REF /Gy`), not source edits.

`.ignore` at the repo root hides the inert directories from `rg`/Grep by default. Use an
explicit path (or `rg --no-ignore`) when you actually need to read LLVM optimizer/backend code.

## Correctness constraints on any optimization

- `tests/gold_link.ps1` / `tests/windows_correctness.ps1` require byte-identical output against
  reference `lld-link` and across build-N/build-M. Optimizations must be output-preserving.
- Allocator is `mimalloc-pprof` with `MI_MALLOC_OVERRIDE=1`; `tools/verify.py` enforces exactly one
  mimalloc TU. `tests/windows_allocator_benchmark.ps1` is the existing wall/CPU/RSS benchmark
  (2048-object fixture, 5 repeats, bootstrap CI) — extend it rather than writing a new harness.

## Build

CMake + Ninja on MSVC (VS generator unsupported). `-DCMAKE_{C,CXX}_COMPILER_LAUNCHER=sccache`
for warm rebuilds. Linux-to-Windows cross via `cmake/WinMsvcCross.cmake` + xwin; see `README.md`.
